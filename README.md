# VipCars Tool

VipCars scraper, HTML report publisher, pricing recommendations, and global rate import generator.

## Local run

```powershell
npm install
npm run vipcars
npm run vipcars:report
npm run vipcars:recommendations
python -m pip install -r requirements.txt
npm run vipcars:rates
```

The recommendations command derives the required coverage matrix from `vipcars.config.example.json` and refuses to generate output when locations, durations, or the pickup-date count do not match the scrape plan.

## GitHub Pages

The workflow `.github/workflows/vipcars-daily.yml` publishes:

```text
https://prejsik.github.io/VipCars-tool/report.html
https://prejsik.github.io/VipCars-tool/vipcars-recommendations.xlsx
https://prejsik.github.io/VipCars-tool/vipcars-rates-import-ready.xlsx
```

The HTML includes every planned date/duration/location from coverage, even when no offers were collected. Incomplete checks and verified empty searches are distinguished; an unsuccessful check is not reported as confirmed absence of MM Cars. A partial report cannot reconstruct prices that were never fetched. The import XLSX is published only when baseline validation, workbook generation and at least one complete pricing band have been verified. A baseline-only workbook remains in the run artifacts for diagnosis, not on Pages or as an import link in Telegram.

`vipcars-recommendations.xlsx` is the control workbook with changed positions, recommendation details, and validation. `vipcars-rates-import-ready.xlsx` keeps the current 12-column `RateGroup Export` layout from `RateGroup Export (6).xlsx`, with duration bands `1`, `2-6`, `7-8`, and `9+`, and contains only the clean import sheet. Headers are checked against the configured duration bands before any rate is changed. Both output workbooks show all rate rows on opening: source filter criteria, sorting and hidden-row flags are cleared, and the filter dropdowns cover the full expanded grid. This does not alter any rate or the source workbook.

The import is one global workbook divided by the `Rate zone` column. For each zone, pickup date and enabled duration band, all twelve approved groups receive the SAME absolute net EUR/day price, not a percentage change from their old prices. The groups are `CDMR`, `CFAR`, `CFAR1`, `CFAR2`, `CFMR`, `CWAR`, `CWAR1`, `CWAR2`, `CWAR3`, `CWMR`, `EDAR`, and `EDMR`, with no premiums. The exporter enforces this allowlist in code for every location and duration band; adding any other group to the configuration rejects the export before rates are changed. All other groups are untouched. This explicitly includes some manual-transmission import groups, but the market benchmark is always the automatic-offer result set; this is not a separate competitor ranking for each vehicle class.

The permanent policy aims at top1, otherwise top2, otherwise top3, at 0.50 EUR gross/day below the relevant competitor. It can raise or lower rates, subject to the protected holiday baseline minima below. The old 2.50 EUR gap trigger and 0.70-1.60 adjustment limits do not apply. There are no city/airport or other seasonal pricing rules. Column `1` remains unchanged; `2-6`, `7-8`, and `9+` are updated. The `9+` price is calculated from all six checked durations, 9-14 days. The template has one open-ended `9+` column: these checks do not verify competitor ranks for rentals longer than 14 days. An optional van/premium or any-transmission scrape can still produce an HTML report, but cannot generate this global pricing import.

For pickup dates **2026-10-31 through 2026-11-01**, **2026-11-11**, and **2026-12-15 through 2027-01-01**, inclusive, the current baseline's net EUR/day prices are additional minima in all zones and enabled bands. The common class floor is the highest baseline price among the twelve approved groups for that date, zone and band, rounded UP to three decimals. It is applied before choosing top1, top2 or top3, together with the existing PLN gross floor and the observed broker markup. If top3 is infeasible, the entire scope keeps its individual baseline prices; otherwise increases are allowed, but no approved class can be lowered below its baseline. The exporter independently guards the final cell writes and records protected constraints in the validation sheet. Protection follows the pickup date, not holidays crossed during a rental. Replacing the baseline updates these minima; it does not infer new protected dates from rate changes.

Every duration in a band must have complete, valid data for that zone, and the number of saved offers must match its coverage record. For each duration the engine finds the best attainable rank, respecting the minimum after import rounding. The shared price is the lowest of those per-duration caps, so it meets all their rank constraints. The exporter independently checks every predicted gross price and minimum at the final shared rate. If any duration lacks a valid target, including when its floor blocks top3, the entire band retains its baseline prices. Workbook generation also requires all configured locations. Blocked bands are explicitly shown in the review and validation sheets.

For every MM Cars Rental offer the scraper reads `Pay Now` from the same card. With gross total `T` and Pay Now `P`, the observed broker multiplier is `m = T / (T - P)`. The net import cap for a gross daily site target `S` is `S / m / 1.23`. The predicted site price is `net import * 1.23 * m`. This assumes the observed percentage markup persists at the proposed price, not that Pay Now remains a fixed amount; it is an estimate rather than a guarantee of a future live rank. MM's current rate and valid Pay Now are mandatory. Missing/invalid amounts, mixed currencies, incomplete data, and broker multipliers outside `1.00-1.25` block the affected band. No historical or default broker markup is substituted.

For pickup dates through **2026-10-25 inclusive**, MM must retain at least **30 PLN gross/day after the broker deduction for 2-6 days**, and **40 PLN gross/day for 7-8 days**. For pickup dates **from 2026-10-26 onward**, the minimum is **40 PLN gross/day for every enabled band: 2-6, 7-8 and 9+**, with no expiry. For **9+ days the 40 PLN gross/day floor also applies before that date**. Their net EUR floors are respectively `30 / EURPLN / 1.23` and `40 / EURPLN / 1.23`. In `minimum_rates.bands`, an optional `start_date` sets the inclusive first pickup date, a null `max_days` means no upper duration limit and a null `end_date` means no expiry; bands without an `end_date` inherit the existing overall expiry. The shared-price and rank policy continue for all enabled bands. Rates must always remain positive. Caps round DOWN and floors round UP to the import's three decimal places. Even a baseline with extra decimal places is set to the exact shared rate to avoid breaking group parity.

The current baseline remains in use until the user explicitly supplies a replacement baseline. Generated recommendations or import workbooks are not automatically promoted to the baseline. When a band is blocked, its existing baseline rates are preserved; the minimum does not force a change to those untouched rates.

The CLI fetches the latest published average EUR rate from the [NBP Table A API](https://api.nbp.pl/). A failed or invalid response uses the user-approved fallback **1 EUR = 4.30 PLN**. Each payload and review records the rate, source, publication date when available, and fallback reason. Old percentage-model recommendation JSON is rejected; regenerate it with the current code. The report distinguishes individual market targets before holiday protection from the final shared band price, predicted site prices and verified ranks. `Target rank` and `Reason` describe the final band decision, including protected baseline minima; blocked rows have no target rank and explain why the baseline was retained. `Minimum MM gross PLN/day` includes the holiday net minimum converted to supplier gross PLN when it is higher than the standard floor. Existing HTML gap colors remain observations of the scraped prices, not pricing instructions.

Recommendations and import rows are separated by the VipCars rate zones configured in `vipcars-rate-update.config.json`: `BYD`, `GDA`, `KAT`, `KRA`, `POZ`, `WAR`, and `WRO`. The generated import remains one `RateGroup Export` worksheet with 12 columns; the `Rate zone` column identifies the city-specific row. `Recommendations Review` shows the scraper location, zone code, zone name, and metroplex for every decision.

## Scheduled scenarios

The daily schedule requests a start at **16:30 Europe/Warsaw the previous afternoon** to prepare the next morning's report before 07:00. It runs entirely on GitHub-hosted runners; the user's computer is not required. GitHub handles summer/winter time through the workflow's `timezone` setting; there is one scheduled run per day.

The run reported on October 6, 2026 was created at 01:10 Warsaw time, nearly six hours after the old 19:17 trigger, and its scrape stage lasted about 12 hours 53 minutes. Publication took under a minute; Telegram arrived around 14:06 Warsaw time. The earlier start adds 2 hours 47 minutes of headroom, but does not by itself remove that full delay. GitHub schedules are best-effort, so 07:00 remains a delivery target, not a guaranteed deadline. There is no independent cloud trigger or forced partial publication at 07:00. Telegram is sent as soon as the report is published, which may be during the night.

The daily scan checks all seven locations, 45 rolling pickup dates and rental durations from 2 to 14 days, in EUR with automatic transmission: 4,095 searches. The scheduled plan uses the original workflow creation timestamp in Warsaw: at or after 16:30 it starts with the next calendar day; before 16:30 it starts with that day's morning-report date. Reruns keep that original reference, even after midnight. Manual/push runs retain the 10:00 pickup cutoff, also anchored to their original creation time. The prepare job fixes explicit dates and creates 225 jobs, grouped by pickup date and import band (2-6, 7-8, 9-14), with at most 21 searches per job. Twelve jobs can run in parallel. Every planned search occurs exactly once in the first pass. The earlier start means prices may be collected the previous afternoon or during the night.

## Scraper reliability

Each CLI process (one workflow chunk) owns one Chromium browser and opens an isolated context for every search attempt. The first pass attempts every planned check once. At most two subsequent recovery passes retry eligible failures, with a shared limit of three attempts per location/date/duration check. Successful checks are not repeated.

Navigation retains the configured `timeoutMs` (45 seconds by default). Initial result detection can use at least half of the shared attempt budget, capped by the remaining attempt/job deadline. The local default remains 180 seconds per attempt (`--attempt-budget-ms`); the workflow uses 240 seconds including pagination. The attempt budgets for at most 21 searches sum to 84 minutes, leaving more room for recovery within the 170-minute job budget (`--job-budget-ms`) and workflow's 180-minute limit. This arithmetic excludes cleanup and server cooldowns; it is not a guarantee that every first-pass search will finish. Result GET requests remain serialized with three seconds between starts across attempts and scenarios in the same CLI process. This is conservative pacing, not a documented VipCars rate limit or a guarantee of live availability. HTTP Retry-After cooldowns are respected; do not rotate accounts or addresses to evade them. Slow searches can still fail, and recovery passes use only the remaining job time. Failure-artifact capture and context cleanup have separate short limits. Unfinished checks remain explicitly incomplete, never valid empty results. Checkpoints are saved after each location.

Results require a verified complete result state; an unchanged card count alone is not evidence of completeness. Failure artifacts have separate attempt numbers and include stage timings, selected network events and JavaScript errors. Diagnostic JSON omits full URL query strings, request bodies, headers and cookies; only allowlisted result type and numeric pagination fields are retained. HTML and screenshots remain workflow debugging artifacts and are not sanitized; treat downloaded artifacts accordingly. The publish job installs Node dependencies independently of the scrape jobs.

`TIMING` lines and failure diagnostics break network pagination into `network_throttle_wait`, `network_http_fetch`, `network_parser`, `network_dom_parity`, `network_prep` and `network_transport_wait`. These are bounded aggregate totals, not a log for every page. `pageCount` counts validated pages; `cooldown_wait_ms` separately records waiting before an attempt. The enclosing `network_offers` total includes these phases and must not be added to them. Instrumentation does not remove pacing or prove a live speed increase; it identifies which phase needs further investigation.

Both browser and experimental network paths observe failed result requests. Chromium extra response information exposes HTTP status and Retry-After even when CORS hides the normal response. A valid Retry-After on any error response (including the observed HTTP 400) pauses subsequent scenarios and retries in that process. The CLI persists an increased cooldown immediately in the resume checkpoint, before the attempt returns. No new attempt is consumed while waiting, and a cooldown longer than the remaining job budget leaves checks incomplete without more requests. Cooldowns and request pacing are not shared between separate GitHub jobs or independent processes. Without Retry-After, network failures, HTTP 429 and 5xx remain eligible for the existing bounded retries; other 4xx failures are not retried. Intentional request cancellation and unrelated resource failures are ignored. This respects a server-requested pause but does not guarantee complete live results. The DOM-pruning experiment was removed after live validation still failed at 300 of 471 offers.

The scraper verifies the effective page form against the requested airport IDs, dates, times and currency. MM Cars' cheapest matching offer is retained even when it falls outside the competitor limit.

The workflow enables `--network-results` for automatic-transmission searches after the bounded live validation below. Standalone CLI use remains opt-in; workflow searches with `transmission=any` retain the UI path. In automatic mode it applies the UI transmission filter first, then captures the filtered first response. The request must match the search contract, request only automatic transmission, and contain no supplier or category exclusions. Its offer fields and total count must match the first rendered page. If the UI filter is unavailable, the path collects the full unfiltered search and filters transmission locally. Subsequent pages are downloaded sequentially using browser-native fetch in that session, retaining three-second request pacing. Direct HTTP-client pagination returned HTTP 400 in live tests and is not used. Response HTML is parsed without executing its scripts or appending cards to the live page. Every page must retain the same total, advance its cursor, and provide distinct offer IDs; incomplete, inconsistent, or mixed-transmission filtered pages fail the check. All matching pages are collected before choosing each provider's cheapest offer and applying the configured category. First-page parity is checked; this is not an independent visual verification of every later offer. Offline integration tests are not evidence of live-site support or speed.

The filtered request must also use the full minimum/maximum price range declared by the page's slider, including when the UI reports no results. Missing, ambiguous, or narrowed bounds fail the check. Controlled pagination waits for both the fetch result and its matching Chromium request lifecycle, so delayed server cooldown metadata takes precedence over a generic fetch failure. A canceled controlled request fails promptly instead of waiting for the whole search budget; unrelated intentional cancellations remain ignored.

Filtered pagination uses the page's native continuation parameters and JSON query format, matching its Chromium `filter_search` path. The first filter-click request is retained for DOM verification, but is not reused as the pagination template. Search and filter values must agree before continuation; encoded session values are decoded once. Diagnostics record only result type, numeric page/cursor and response wait time, without session values. These contract checks pass offline; the 2026-10-03 production test of the preceding implementation still completed only 54/273 checks, so this repair requires fresh live validation after the active server cooldown expires.

Search bootstrap requests (`sub_step1`) share the same request pacing, transport-failure observation and Retry-After handling as offer requests, but are never accepted as offer pages. In one failed production chunk all 42 attempts stopped before offers loaded: bootstrap XHR failed with CORS errors while the scraper previously waited 120 seconds for a result. Observing bootstrap failures avoids that blind wait; it does not repair the provider's CORS response or guarantee availability.

An earlier filtered-response prototype reached 300 of 445 offers before an HTTP 400 with Retry-After: 3600. After that cooldown expired, a default-UI test with three-second pacing still exceeded its 180-second search deadline; the last observed count was 310 of 445 offers. No HTTP 400 or server cooldown was recorded during that attempt, but intervals between the final successful responses grew to 12-14 seconds. These UI failures motivated the filtered-response path.

On 2026-09-28, one authorized local search using the new filtered-response path completed **465/465** automatic offers in **156.066 seconds**, while the live DOM retained ten cards. Scope: Warsaw Chopin, 2026-10-02 to 2026-10-04, 10:00, EUR. MM Cars was retained among the 25 provider results, including its Pay Now amount. No publication or Telegram was performed. This validates that one search, not all seven locations, every duration, or the throughput of the full 5,460-check daily run.

To continue an interrupted local run, repeat its exact CLI arguments with `--resume`. The canonical checkpoint is `<output-coverage>.resume.json`. Local resume requires the same planned dates, durations, locations, currency, times and filters, the same Warsaw calendar day, and a checkpoint at most six hours old. It preserves the original job deadline and the three-attempt limit, and skips completed checks. A fresh run without `--resume` starts a new checkpoint.

On a GitHub rerun (including **Re-run failed jobs**), each retried chunk restores its latest previous-attempt artifact from the same workflow run. Cloud checkpoints are additionally bound to the run ID and commit SHA, with a 24-hour freshness limit that permits overnight recovery. A later GitHub attempt gets a fresh process time budget, but retains completed results, server cooldowns, non-retryable failures and the cumulative three-attempt limit. Missing, expired or invalid checkpoints stop that chunk instead of silently starting over; this also means that a rerun cannot start a previously skipped chunk with no checkpoint. Restored CSVs are preserved before setup and regeneration so a later startup error does not discard already collected data. A new workflow run never reuses yesterday's prices. Chunk, merged and Pages artifact names include the attempt number; publication selects only the latest artifact per chunk, so old and resumed results are not duplicated. No extra retry workflow is automatically dispatched.

Install the test browser with `npx playwright install chromium`, then run `npm run test:all` for the offline regression suite, including local Chromium result-page fixtures. These tests do not send Telegram messages or query live rental offers. They verify retry, deadline and completeness behavior, not a guaranteed live-site response time.

## Telegram notification

The workflow sends a Telegram message after the GitHub Pages report is deployed, when these repository secrets are set:

```text
TELEGRAM_BOT_TOKEN
TELEGRAM_CHAT_IDS
```

`TELEGRAM_CHAT_IDS` can contain one chat ID or several IDs separated with commas, for example `123456789,987654321`.
The older single-recipient `TELEGRAM_CHAT_ID` secret is still supported as a fallback.
The message also lists every attempted pickup date where MM Cars Rental is not visible in any scraped location or rental duration.
It includes a direct HTML link and reports verified durations, blocked pricing bands and changed price cells. An import link requires successful generation against a confirmed baseline and at least one verified pricing band; zero changes can still be valid if verified prices already match the baseline. Missing/invalid summaries and baseline-only results hide the import link. Partial imports explicitly warn that blocked scopes retain baseline rates. Both attempt timeouts and initial-search "timed out" errors are counted. The merged backup contains output files only; raw chunk diagnostics remain in their separate chunk artifacts, avoiding a second multi-gigabyte upload before notification.

The message follows the DiscoverCars layout: actual pickup dates, compact rental durations, the share of planned checks that returned complete nonempty price results, and actual Excel increases/decreases, followed by Import, Recommendations and Price report links. Average changes are shown in net EUR/day, matching VipCars import units. Statistics come from changed workbook cells, not preliminary market decisions. Incomplete or blocked runs are explicitly labeled and retain MM availability warnings, timeout counts, workbook publication gates and diagnostic links. A complete empty search is not counted as obtained price data. Older summaries without detailed change statistics show only their verified total; no breakdown or average is invented.

## Baseline safety

The user-provided import template is stored as `input/vipcars-rate-group-export.xlsx`. Its approved SHA-256 is stored in `input/vipcars-baseline-manifest.json`; generation fails before writing outputs when the file does not match the manifest. The manifest must also have status `confirmed_imported` or `verified_live`, a timezone-aware `confirmed_at` timestamp and a nonempty `confirmed_by`. A matching hash alone does not establish that these are the current rates in Wheels. An unconfirmed `user_provided` baseline remains blocked; do not invent confirmation metadata to bypass this gate.
The current source is `RateGroup Export (6).xlsx`, supplied by the user on 2026-10-05 and approved after auditing. The user confirmed that decreases in the export are intentional and that its holiday prices are minima. Its `verified_live` status records user confirmation, not a direct inspection of Wheels. The baseline is a byte-identical copy of the source: 15,747 daily rows, valid zones, no duplicate date/group/zone entries and no excluded source rows. The twelve approved classes cover every zone from 2026-10-05 through 2027-01-13; `FVMD` has longer coverage in its supplied zones. The manifest records the source and workbook hashes. Previous exports are no longer used.
The generator also fails when a planned date, duration band, or approved group is absent from that baseline. After importing a generated workbook or changing rates outside this tool, replace the baseline and its manifest before using a later recommendation; the repository cannot detect an external import by itself.
